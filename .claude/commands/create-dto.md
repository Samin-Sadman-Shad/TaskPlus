# /create-dto

Create the **API contract types** for the REST endpoints. Following CQRS, writes and reads get
**separate** DTOs: one for create, one for update, and one or more for reads. DTOs are derived from
the domain classes but expose **only** what the client needs.

**Scope:** `$ARGUMENTS` — if empty, generate every DTO group below. Otherwise generate only that group.

## 0. Read context first

1. `CLAUDE.md`
2. `docs/DOMAIN-MODEL.md` — the **DTO exposure** column (R / C / U / —) decides every field
3. `docs/CONVENTIONS.md` — naming
4. The entities in `src/SmartTask.Domain/Entities/` and models in `src/SmartTask.Application/Common/Models/`
5. Existing files under `src/SmartTask.Application/DTOs/`

If the Domain layer is missing, stop and ask the user to run `/create-domain` first.

## 1. The exposure rules (apply to every DTO)

**Never** put these in any DTO:
- `PasswordHash`, `NormalizedEmail`, `RefreshTokens`, `TokenHash`, `ReplacedByTokenHash`, `CreatedByIp`
- `IsDeleted`, `DeletedAt`, `DeletedBy`
- `CreatedBy`, `UpdatedBy`
- `RowVersion`
- Navigation properties as entities (flatten to `OwnerName`, `AssigneeName`, or a nested **DTO**)

**Create DTOs** must not contain:
- `Id` (generated by the domain)
- Audit fields, `CompletedAt`
- `OwnerId` (comes from the authenticated user)
- `ProjectId` for tasks (comes from the route `api/v1/projects/{projectId}/tasks`)
- `Status` (new tasks always start as `ToDo`)
- `Role` on registration (privilege escalation risk — new users are always `TeamMember`)

**Update DTOs** must not contain:
- `Id` (comes from the route), `OwnerId`, `ProjectId`, audit fields
- `Status` or `AssigneeId` — those have their own action DTOs and endpoints (`PATCH .../status`,
  `PATCH .../assignee`) so they can carry different permissions (a TeamMember may change status of
  their own task but not edit its details).

**Read DTOs** contain only fields marked **R**, plus useful computed/flattened values
(`FullName`, `OwnerName`, `AssigneeName`, `IsOverdue`, counts).

If you think a field should be exposed that the spec marks "—", don't add it — list it in the summary
as a question.

## 2. Shape and style

- `public sealed record`, file-scoped namespace `SmartTask.Application.DTOs.<Feature>`.
- Positional records for small read DTOs are fine; for request DTOs use `init` properties so the JSON
  binder and FluentValidation read cleanly:
  ```csharp
  public sealed record CreateProjectDto
  {
      public string Name { get; init; } = string.Empty;
      public string? Description { get; init; }
      public DateOnly StartDate { get; init; }
      public DateOnly? EndDate { get; init; }
  }
  ```
- Use the domain enums directly (`TaskItemStatus`, `TaskPriority`, `UserRole`); the API serialises them as strings.
- Use `IReadOnlyList<T>` for collections in read DTOs.
- XML `<summary>` on each DTO saying which endpoint uses it.
- No attributes for validation — validation is done by `/implement-validators`.

## 3. DTOs to create

Location: `src/SmartTask.Application/DTOs/<Feature>/`

### Users/
| DTO                 | Fields |
|---------------------|--------|
| `UserDto` (read)    | Id, FirstName, LastName, FullName, Email, Role, IsActive, LastLoginAt, MustChangePassword, CreatedAt |
| `UserSummaryDto`    | Id, FullName, Email, Role — used inside other DTOs and lookups |
| `UpdateUserProfileDto` | FirstName, LastName |
| `ChangeUserRoleDto` | Role (Admin-only endpoint) |
| `CreateUserDto` | FirstName, LastName, Email, Password, ConfirmPassword, Role (Admin-only `POST users`; `Role` has no default, so a missing role fails validation). Redact both passwords in `ToString()` |

Self-registration uses `RegisterRequestDto` and never carries a role. `CreateUserDto` is the **only**
request DTO allowed to carry `Role`, because only an Admin can send it.

### Auth/
| DTO                      | Fields |
|--------------------------|--------|
| `RegisterRequestDto`     | FirstName, LastName, Email, Password, ConfirmPassword |
| `LoginRequestDto`        | Email, Password |
| `ChangePasswordDto`      | CurrentPassword, NewPassword, ConfirmNewPassword — redact all three in `ToString()` |
| `AuthResponseDto`        | AccessToken, AccessTokenExpiresAt, User (`UserDto`) |

Refresh and logout have **no request body**. The refresh token travels only in an HttpOnly cookie
(see `/implement-auth`), so there is no refresh-token DTO and `AuthResponseDto` must not contain it.
Add a `<remarks>` on `AuthResponseDto` saying so. Override `ToString()` on request DTOs carrying
`Password` to redact it, so it can't leak into logs.

### Projects/
| DTO                  | Fields |
|----------------------|--------|
| `CreateProjectDto`   | Name, Description, StartDate, EndDate |
| `UpdateProjectDto`   | Name, Description, StartDate, EndDate |
| `ProjectDto` (details) | Id, Name, Description, StartDate, EndDate, Owner (`UserSummaryDto`), Members (`IReadOnlyList<ProjectMemberDto>`), TaskCount, CompletedTaskCount, CreatedAt, UpdatedAt |
| `ProjectSummaryDto` (list) | Id, Name, StartDate, EndDate, OwnerName, TaskCount, CompletedTaskCount, MemberCount, CreatedAt |
| `ProjectMemberDto`   | UserId, FullName, Email, JoinedAt |
| `AddProjectMemberDto`| UserId |

### Tasks/
| DTO                   | Fields |
|-----------------------|--------|
| `CreateTaskDto`       | Title, Description, Priority (default `Medium`), DueDate, AssigneeId |
| `UpdateTaskDto`       | Title, Description, Priority, DueDate |
| `UpdateTaskStatusDto` | Status |
| `AssignTaskDto`       | AssigneeId (nullable — null unassigns) |
| `TaskDto` (details)   | Id, ProjectId, ProjectName, Title, Description, Status, Priority, DueDate, IsOverdue, Assignee (`UserSummaryDto?`), CompletedAt, CreatedAt, UpdatedAt |
| `TaskSummaryDto` (list) | Id, ProjectId, Title, Status, Priority, DueDate, IsOverdue, AssigneeName |

### Dashboard/
| DTO                 | Fields |
|---------------------|--------|
| `DashboardStatsDto` | TotalProjects, TotalTasks, TasksByStatus (`IReadOnlyDictionary<TaskItemStatus,int>`), TasksByPriority (`IReadOnlyDictionary<TaskPriority,int>`), CompletedCount, PendingCount, OverdueCount, UpcomingDueTasks (`IReadOnlyList<TaskSummaryDto>`) |

Ensure every enum value appears in the dictionaries (zero if no tasks) so the frontend chart is stable.

### Ai/
| DTO                              | Fields |
|----------------------------------|--------|
| `ImproveDescriptionRequestDto`   | Title (optional context), Description |
| `ImproveDescriptionResponseDto`  | OriginalDescription, ImprovedDescription, Suggestions (`IReadOnlyList<string>`) |

### Query parameters
Do **not** create separate query DTOs — the controllers bind `ProjectQueryParameters`,
`TaskQueryParameters` and `UserQueryParameters` from `Common/Models` directly (`[FromQuery]`).
If those are missing, create them as described in `.claude/commands/create-repositories.md` §3.

## 4. Mapping (entity / read model → read DTO)

Create one static class per feature, e.g. `DTOs/Projects/ProjectMappings.cs`:

```csharp
public static class ProjectMappings
{
    public static ProjectDto ToDto(this Project project) { ... }
    public static ProjectSummaryDto ToSummaryDto(this ProjectListItem item) { ... }
}
```

Rules:
- Explicit, hand-written mapping — no AutoMapper, no reflection.
- Mapping is **one-way: domain → read DTO**. Create/Update DTOs are **not** mapped onto entities;
  services call the entity's `Create(...)` / `Update(...)` methods so invariants are enforced.
- Methods that need "today" (e.g. `IsOverdue`) take `DateOnly today` as a parameter — no clock calls.
- Guard against null navigations that the repository contract doesn't promise to include; prefer
  making the contract include them over defensive defaults.
- Add `PagedResult<T>.Map(...)` usage examples in XML docs where list mapping happens.
